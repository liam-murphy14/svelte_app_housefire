# Property facts database migration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add and apply the missing PostgreSQL `Property.facts` schema change so property pages can read records without Prisma column errors.

**Architecture:** Keep `Property.facts` as the existing non-null Prisma `Json` field with an empty-array default. Track the database change as a Prisma migration, expose `prisma migrate deploy` through an npm script, and run that script against the direct database connection before the updated application serves requests. Runtime queries continue using `DB_URL`.

**Tech Stack:** Prisma 7, PostgreSQL/JSONB, npm scripts, SvelteKit, Vitest/unit checks, TypeScript, ESLint, Prettier.

## Global Constraints

- Keep server-only code under `src/lib/server` or server route files.
- Treat `prisma/schema.prisma` as the source of truth for database models.
- Do not hand-edit `src/lib/utils/prismaGeneratedZod/index.ts`.
- Do not commit `.env`, `.env.*`, build output, or generated SvelteKit output.
- Use `DB_URL_DIRECT` for Prisma CLI migration commands and keep runtime Prisma on `DB_URL`.
- Run the narrowest relevant checks while iterating, then run the full applicable checks before claiming completion.

- [ ] **Step 2: Run the failing schema assertion before changing the database**


Expected before the fix: the query returns no row, confirming the production error’s missing-column condition. If the configured database already contains the column, record that result and use migration status instead of applying a duplicate change.

### Task 2: Add the tracked migration and deployment command

**Files:**

- Create: `prisma/migrations/20260731200000_add_property_facts/migration.sql`
- Modify: `package.json` scripts
- Modify: `AGENTS.md` database setup and command guidance

**Interfaces:**

- Consumes: The existing `Property.facts Json @default("[]")` declaration in `prisma/schema.prisma`.
- Produces: A migration deployable by `npm run db:migrate` that adds a non-null JSONB column with an empty-array default.

- [ ] **Step 1: Add the migration SQL**

Create `prisma/migrations/20260731200000_add_property_facts/migration.sql` with:

```sql
-- Add the facts field introduced in prisma/schema.prisma.
ALTER TABLE "Property"
ADD COLUMN "facts" JSONB NOT NULL DEFAULT '[]'::jsonb;
```

The SQL must use the exact quoted table and column names generated by Prisma and must not drop or rewrite existing property data.

- [ ] **Step 2: Add the explicit migration npm script**

Add this script to `package.json` without changing the existing build command:

```json
"db:migrate": "prisma migrate deploy"
```

Do not make `npm run build` require a database connection; releases should invoke `npm run db:migrate` as a separate pre-deploy step with `DB_URL_DIRECT` configured.

- [ ] **Step 3: Update repository guidance**

Update `AGENTS.md` so it no longer says there are no tracked Prisma migrations or that schema synchronization is only implicit. Document:

```text
npm run db:migrate
```

as the command that applies tracked migrations through `DB_URL_DIRECT`, and state that it must run before deploying application code that depends on a new schema field.

- [ ] **Step 4: Validate the migration structure without applying it twice**

Run:

```bash

npx prisma migrate status
```

Expected: schema validation succeeds, the migration is recognized, and Prisma reports the database’s current migration state without an unapplied SQL syntax error.
